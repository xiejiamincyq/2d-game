# 美术资源生产计划：预览选择驱动

## 1. 目标

为《废土清剿协议》建立一套可审查、可追溯、可在 Godot 实际运行尺寸下验收的美术生产流程。所有角色、战斗特效、环境和 UI 的风格决定都必须先向用户展示 `3` 个预览方向；用户明确选择或要求迭代后，才能锁定风格并制作该批正式资源。

本计划只安排美术资源的设计、生成、审查和导入，不修改碰撞、伤害半径、移动、UI 行为或其他玩法逻辑。

## 2. 固定视觉与技术边界

- 镜头：俯视或俯视三分之四视角，所有角色保持一致。
- 基础画面：暗色赛博废土，1280×720 基准视口。
- 色板：黑蓝 `#061019`、主青 `#33fff2`、辅洋红 `#f559bf`、武器/警告橙 `#ff571f`；酸绿只用于毒液、治疗或明确毒性提示。
- 材质：磨损复合装甲、氧化金属、暗色陶瓷、烟熏玻璃、裸露能量导管和积尘合成织物。
- 可读性：外轮廓干净，细节集中在大形体内部；背景对比度低于角色、危险、拾取物和 HUD 状态。
- 运行时路径使用小写蛇形命名，分别存入 `res://assets/art/actors/`、`effects/`、`pickups/`、`environment/` 和 `ui/`。
- 隔离主体和 UI 组件使用透明 PNG；战场背景使用不透明图；UI 面板禁止烘焙文字并需支持九宫格。
- 不覆盖已批准资源。实质性修改必须产生新的草稿版本，同时保留稳定 `asset_id` 和提示词谱系。

## 3. 用户决策协议

### 3.1 每个风格门的预览流程

1. 检查对应场景、程序化绘制、碰撞尺寸、运行时用途和现有色彩语义。
2. 为预览建立草稿 manifest，填写尺寸、运行时目标、背景、路径、色板、光照、提示词、负面约束、模型和授权状态。
3. 验证 manifest；验证失败时不生成图片。
4. 准备 `3` 个有明确差异、但内容和镜头一致的预览方向：`A`、`B`、`C`。
5. 每个方向同时展示源图预览和实际游戏尺寸缩略图；需要时补充透明背景检查或场景合成图。
6. 停止生产并等待用户明确回复：选择 `A/B/C`、组合指定特征，或要求新一轮预览。
7. 用户选择后记录批准方向、保留特征和拒绝特征，状态进入 `style-approved`。
8. 只扩展已批准方向。若后续改动触及镜头、材质、形体语言、色板或光照，重新开启 `3` 图预览门。

### 3.2 不视为风格变更的调整

以下调整可在锁定风格内迭代，不需要重新提供三个方向，但仍需展示修改稿：

- 清理透明边缘、意外边框和小面积伪影；
- 调整枢轴、透明留白和裁切；
- 在不改变形体语言的前提下提高运行时轮廓可读性；
- 降低过强 bloom、背景噪声或装饰对比度；
- 修复九宫格边缘、图标居中或标签留白。

### 3.3 必须重新预览的变化

- 改变俯视角度或角色朝向规则；
- 改变整体插画/像素化/写实程度；
- 改变阵营主色、材质体系或共享光照；
- 改变 UI 形体、边框语言或图标家族；
- 改变环境的地貌、时代感或建筑语言；
- 新增与已有家族明显不同的首领或玩法主题。

### 3.4 完成后的邮件通知

- 每个可验收任务、风格门或正式资源批次在验证、提交并推送完成后，向当前已连接 Gmail 账户的本人地址发送一封完成通知。
- 邮件主题统一使用 `[废土清剿协议] <任务或批次> 已完成`。
- 正文至少包含完成范围、验证结果、Git 提交、下一步和需要用户决定的事项。
- 有适合审查的对比图时附上最小必要附件；不附临时生成文件、凭据、缓存或无关资料。
- 中间进度、生成排队和失败尝试不发送邮件，避免重复通知。
- Gmail 不可用或发送失败时必须在当前任务中明确报告，不得声称已经发送。

## 4. 依赖顺序

```text
风格与技术基线
  -> 角色/战斗预览门
      -> 角色风格锁定集
      -> 战斗特效预览门
      -> 第一批完整资源与游戏内验收
          -> 环境预览门
          -> 环境锁定集与游戏内验收
              -> UI 预览门
              -> UI 锁定集与响应式验收
                  -> 全局一致性与授权验收
```

下一批不得在上一批通过用户批准和游戏内验收前开始。未来的传送门、超载、最终首领和三条终极进化资源，在对应玩法合同稳定后另开预览门，不提前混入当前批次。

## 5. 分阶段任务

### Task ART-1：建立资产台账与预览模板

**目的：** 建立资产 ID、manifest、版本、审查状态和用户选择记录，确保每次生成可追溯。

**验收标准：**

- [ ] 当前角色、敌人、弹丸、拾取物、特效、环境和 UI 资源都有稳定 `asset_id`、运行时路径和目标尺寸。
- [ ] 预览记录能保存 A/B/C 的提示词、缩略图、用户选择、保留特征和拒绝特征。
- [ ] 所有 manifest 均通过项目验证脚本，授权状态未批准的资源不能标记 `final`。

**验证：** 运行 `python .agents/skills/godot-neon-art-pipeline/scripts/validate_manifest.py <manifest.json>`，人工检查路径、尺寸和审查状态。

**依赖：** 无

**规模：** S

### Task ART-2：角色与敌人风格预览门

**目的：** 用同一内容集提供三个角色视觉方向，先决定镜头、轮廓、材质、阵营色和细节密度。

**预览内容：** 每个方向包含玩家、Scrapper、Bruiser 和一张基础命中特效；三套使用相同构图、比例和背景检查条件。

**验收标准：**

- [ ] 提供 A/B/C 三个方向以及 64×64、96×96 实际尺寸预览。
- [ ] 三个方向差异可以用镜头、形体、材质、光照和细节密度准确描述，不只是换色。
- [ ] 用户明确选择一个方向或指定组合；未选择前不制作完整角色批次。

**验证：** 人工检查透明边缘、轮廓、镜头一致性、玩家/敌方阵营识别和碰撞中心对齐。

**依赖：** ART-1

**规模：** S

### Checkpoint ART-A：角色风格决定

- [ ] 用户选择 A/B/C 或书面指定组合方向。
- [ ] 记录保留特征和拒绝特征。
- [ ] 玩家、标准敌人、大型敌人和基础命中特效组成的锁定集获得 `style-approved`。

### Task ART-3：完成角色、敌人、武器与拾取物批次

**目的：** 在已选风格内完成当前游戏所需的角色与交互主体。

**范围：** 玩家主体、独立主武器、Scrapper、Dasher、Spitter、Bruiser、废铁无人机、玩家子弹、酸液弹、经验晶片、护盾拾取物。

**验收标准：**

- [ ] 标准角色源图 1024×1024、运行时约 64×64；Bruiser 运行时约 96×96；弹丸/拾取物源图 512×512、运行时 24–48 px。
- [ ] 玩家碰撞中心对应 13 px 半径，标准敌人对应 14 px，Bruiser 对应 24 px；替换美术不改变碰撞或玩法数值。
- [ ] Spitter 的酸绿、玩家武器橙、友方青和敌方洋红在密集战斗中可区分。

**验证：** Godot 实际战斗中检查枢轴、缩放过滤、透明边缘、受击闪白、遮挡顺序和高密度可读性。

**依赖：** Checkpoint ART-A

**规模：** M

### Task ART-4：战斗特效风格预览门与批次

**目的：** 先决定发光核心、碎片、拖尾和烟尘的表现语言，再制作完整战斗特效。

**预览内容：** 每个方向展示枪口火光、命中火花、激光、电弧圆环和地刺中的代表性组合。

**验收标准：**

- [ ] 提供 A/B/C 三套同强度、同尺寸的特效预览，并标出发光层与烟尘/碎片层的拆分方式。
- [ ] 用户明确选择方向后，完成枪口、命中、死亡、玩家受击、护盾吸收/破裂、冲刺拖尾/斩击、激光、电弧、地刺、磁吸拖尾、升级闪光和连杀提示特效。
- [ ] 特效在实际伤害半径下可读，不以大面积不透明烟雾遮挡敌人前摇。

**验证：** 在普通、高射速、五枪线和密集敌群场景检查叠加、透明度、边缘、持续时间和辨识度。

**依赖：** ART-3

**规模：** M

### Checkpoint ART-B：角色与战斗批次

- [ ] 用户批准角色与战斗特效的最终方向。
- [ ] 所有资源达到 `gameplay-approved`，但只有完成授权审查后才进入 `final`。
- [ ] 当前批次通过 Godot 实际尺寸和密集战斗验收。

### Task ART-5：环境风格预览门

**目的：** 决定战场地貌、地面模块、结构物和气氛层的视觉方向，同时保持游戏中心低干扰。

**预览内容：** 每个方向包含 1280×720 战场裁切、一个废土结构和一个大气覆盖层；不包含文字、角色或 UI 框。

**验收标准：**

- [ ] 提供 A/B/C 三个环境方向，并在同一角色/危险标记覆盖下比较对比度。
- [ ] 用户明确选择后，锁定地面纹理、结构材料、线路语言、贴花密度和气氛强度。
- [ ] 可玩区域中心没有高对比杂物、伪命中特效或影响危险识别的发光装饰。

**验证：** 1280×720 和宽屏视口下检查平铺接缝、角色可读性、镜头移动和世界边界衔接。

**依赖：** Checkpoint ART-B

**规模：** S

### Task ART-6：完成环境批次

**范围：** 2–3 款主地面、3–4 款金属/陶瓷地砖、青色能量线路、橙色警戒线路、地图边界直线/转角/节点、8–12 款贴花、6–10 款非阻挡装饰、3–4 款大型结构剪影、2 款尘雾和 2–3 款灰尘/火星粒子。

**验收标准：**

- [ ] 资源可覆盖约 2800×1800 世界，不依赖单张固定 1280×720 背景。
- [ ] 地面和装饰在镜头移动时无明显接缝、重复热点或视差错误。
- [ ] 装饰不引入碰撞，不改变世界边界，不压过角色、拾取物和危险提示。

**验证：** 四边和四角巡检；普通战斗和高密度战斗截图对比；检查过滤与 mipmap 设置。

**依赖：** ART-5 用户选择

**规模：** M

### Checkpoint ART-C：环境批次

- [ ] 用户批准战场裁切、结构和大气覆盖层。
- [ ] 环境在实际游戏中达到 `gameplay-approved`。
- [ ] 角色、特效与环境的对比度层级一致。

### Task ART-7：UI 风格预览门

**目的：** 决定面板形体、按钮状态、HUD 装饰和图标家族。

**预览内容：** 每个方向包含一个九宫格面板、一个按钮五态、生命/护盾/经验三个图标及一张 1280×720 HUD 合成预览。

**验收标准：**

- [ ] 提供 A/B/C 三个 UI 方向；所有组件无烘焙文字，中心标签区域清晰。
- [ ] 用户明确选择面板、按钮、焦点态和图标语言后才扩展完整 UI。
- [ ] 选定方向支持键盘焦点、鼠标悬停、按下和禁用状态的明显区分。

**验证：** 960×540、1280×720、1920×1080、2560×1080 合成预览，检查九宫格角和文字空间。

**依赖：** Checkpoint ART-C

**规模：** S

### Task ART-8：完成 UI 批次

**范围：** 标题徽标、开始背景、HUD 卡片、通用弹窗、升级卡片、连杀框、Toast、按钮五态、生命/经验/护盾条、音量滑杆、HUD 四角/扫描线、准星、Windows 图标、9 个 HUD 图标和 12 个升级图标。

**验收标准：**

- [ ] UI 图标源图 256×256、运行时 24–64 px；面板源图目标 2048×1024，并具有明确九宫格边距。
- [ ] 12 个升级图标分别对应当前升级 ID，均为单一中心符号、单一主强调色、无文字数字。
- [ ] 中文标签在紧凑和宽屏布局下不被装饰挤压，焦点态可见。

**验证：** 四种目标分辨率检查开始、HUD、升级、暂停和结算界面；验证九宫格、按钮状态、图标清晰度和对比度。

**依赖：** ART-7 用户选择

**规模：** M

### Checkpoint ART-D：UI 批次

- [ ] 用户批准面板、按钮和图标家族。
- [ ] 所有 UI 组件通过响应式和实际文本验收。
- [ ] UI 与角色、环境共享色板和材质语言，但不遮挡战斗。

### Task ART-9：全局一致性、授权与最终验收

**目的：** 统一三批资源并完成最终状态审查。

**验收标准：**

- [ ] 所有资源记录提示词谱系、生成模型、来源和授权审查状态；未批准授权的资源不标记 `final`。
- [ ] 无烘焙文字、意外边框、裁切主体、透明光晕、混合镜头、噪声轮廓或过量 bloom。
- [ ] 资源替换不改变碰撞、伤害半径、移动、波次或 UI 行为。

**验证：** 运行相关自动测试和 Godot 烟雾测试；完成四种分辨率人工巡检；审查运行时文件、manifest 和最终 diff。

**依赖：** Checkpoints ART-B、ART-C、ART-D

**规模：** M

## 6. 未来玩法资源门

以下内容只建立待办，不在玩法实现前生成正式资源：

- 传送门：预警、爆发、关闭三个阶段；
- 超载：角色高亮、扩张能量环、屏幕边缘能量和 HUD 槽；
- 三条终极进化：“轨道风暴”“雷网矩阵”“裂地超载”；

## 7. 风险与控制

| 风险 | 影响 | 控制 |
|---|---|---|
| 预览只换色，没有真实选择价值 | 高 | 固定相同内容，要求形体、材质、光照或细节密度存在可描述差异。 |
| 源图漂亮但游戏内不可读 | 高 | 每次预览同时提供运行时缩略图和场景合成图。 |
| 批次之间风格漂移 | 高 | 下一批只能引用已批准 manifest；触及风格字段必须重新开三图门。 |
| 环境抢夺战斗注意力 | 高 | 预览时叠加角色与危险标记，限制中心对比度和高亮。 |
| UI 无法响应式拉伸 | 中 | 使用无文字九宫格组件，在四种视口下提前验收。 |
| AI 透明边缘或结构错误 | 中 | 新版本不覆盖旧稿；检查 alpha、边框、裁切、结构和实际尺寸。 |
| 授权状态不清晰 | 高 | manifest 强制记录来源和授权状态；授权未批准不能进入 `final`。 |

## 8. 完成标准

- [ ] ART-1 至 ART-9 与四个批次检查点全部完成。
- [ ] 每个风格门都有三张预览和用户明确选择记录。
- [ ] 所有正式资源来自已批准方向，并通过 Godot 实际运行尺寸验收。
- [ ] 所有最终资源完成授权审查，没有改变玩法逻辑或混入临时生成状态。

# 技术与视觉恢复实施计划

本计划由 `docs/audits/2026-08-09-technical-visual-audit.md` 驱动。它是现有玩法计划的前置门；在 Checkpoint C 通过前，不进入新的大批量角色美术生产。

## Phase 0：止损与事实校正

### Task V0.1：降级错误审批状态

- 将玩家 turnaround 与 Dasher A/B 从 `gameplay-approved` 降为 `rejected` 或 `draft`。
- 将所有不存在但被标为 `style-approved` 的资源恢复为 `planned`。
- 在旧审查文档顶部增加 superseded/rejected 说明，不删除历史证据。
- 增加登记表路径存在性校验。

验收：登记状态与磁盘文件一致；任何 `gameplay-approved` 条目均能找到运行时截图/视频和用户确认。

### Task V0.2：清理资源与工作区边界

- 定义 source、generated、runtime、preview、archive 五类目录职责。
- 旧 72/120 帧方案移出生产加载路径；保留 Git 历史或 archive 指针。
- `.gitignore` 忽略 Godot `.import` sidecar 和本地临时证据目录。
- 文档和脚本统一 UTF-8。

验收：工作区无生成 sidecar 噪声；每个运行时资源只有一个权威来源和一个 manifest。

### Checkpoint A

- 状态已纠正，没有误导性的 gameplay approval。
- 资源目录和生成物责任清楚。
- 用户确认继续进入新视觉合同。

## Phase 1：视觉合同与技术预览

### Task V1.1：建立共享 45°相机预设

- 固定正交相机、45°俯角、焦点高度、角色世界前方向和帧 0 朝向。
- 固定 64×64 运行时画布、脚底点、碰撞中心和阴影尺寸。
- 建立用于玩家、武器、敌人和预览的唯一渲染场景。
- 添加相机角度和 pivot 自动测试。

### Task V1.2：先出三套玩家技术预览

三套预览必须使用同一人物设计、同一 45°相机和同一动作，区别只在技术方案：

- A：16 方向预渲染，身体与武器分层，方向 socket。
- B：24 方向预渲染，身体与武器分层，方向 socket。
- C：实时 2.5D rig 作为性能与质量对照。

每套都提供正/侧/背/斜向、身体单层、枪械单层、合成、Alpha 检查和 64×64 战场预览。用户选择前不制作完整帧集。

### Task V1.3：建立 Alpha 与层级验证器

- 检查画布尺寸、透明角、主体 bbox、内部 Alpha 中位数和边缘半透明比例。
- 检查身体与枪械 socket 偏差、枪口位置和越界。
- 输出深/浅检查底、碰撞圆、脚底线和层级叠加预览。

### Checkpoint B

- 用户明确选择 A/B/C 技术方案。
- 45°相机、方向数、pivot、socket、Alpha 门全部通过。
- 只有选中方案允许进入生产。

## Phase 2：玩家垂直切片与完整动画

### Task V2.1：拆分玩家视觉控制器

- 新增数据化 `ActorVisualProfile`。
- 新增 `DirectionResolver`、`PlayerVisualController` 和 layer resolver。
- `Player.gd` 只发布移动、瞄准、冲刺、射击、受击状态，不再直接绘制角色和枪械。
- 保留碰撞与数值行为不变，并以测试锁定。

### Task V2.2：完成一个方向的完整垂直切片

- 同一 rig 输出身体与枪械。
- 完成 idle、run、fire/recoil、dash、hit。
- 验证脚不滑、枪不绕圈、背向遮挡正确、Alpha 不漂移。
- 提交至少 5 秒实际运行时片段供用户确认。

### Task V2.3：扩展到已选方向数

- 批量输出所有方向和动作 atlas。
- 为每个方向写入 hand/muzzle socket 和前后层级元数据。
- 对方向边界进行慢速转身检查，防止跳变、闪烁和比例漂移。
- 运行最坏动作/射击压力测试。

### Checkpoint C

- 玩家实际战斗画面经用户批准。
- 45°视角稳定；身体、枪械、手部和枪口关系可信。
- idle/run/fire/dash/hit 完整，无半透明和脚滑。
- 性能与玩法回归测试通过。

## Phase 3：敌人视觉与动画系统

### Task V3.1：建立共享敌人视觉接口

- 新增 `EnemyVisualController` 与按种类配置的 profile。
- 从 `Enemy.gd` 移除按种类绘制矩形和 Dasher 特例。
- 使用共享 hit-flash shader；每实例只更新参数。
- 状态至少包含 idle、move、windup、attack、hit、death。

### Task V3.2：先做 Dasher 动画样板

- A/B 两个外观共享速度和动画合同。
- 保留右向母版/运行时左右翻转策略。
- 完成 6–8 帧移动、突进前摇、攻击、受击和死亡反馈。
- 先给出三套移动节奏预览，用户选择后再正式输出。

### Task V3.3：完成 Scrapper、Spitter、Bruiser

- 每类先出三套风格/轮廓预览，用户选择后制作。
- 各自具备可辨识运动与攻击节奏，而非仅换颜色。
- Spitter 明确远程蓄力/发射；Bruiser 明确重击前摇和恢复。

### Checkpoint D

- 四类敌人不再使用生产矩形占位。
- 移动、攻击前摇和受击在密集战斗中仍可辨认。
- A/B Dasher 都有动画且保持面向玩家。

## Phase 4：战场、VFX 与 HUD

### Task V4.1：制作一块战斗样板地块

- 用 TileMap/分块预烘焙替代大范围矩形网格。
- 建立底色、结构、贴花、发光标记、道具和前景遮挡层。
- 在样板地块中验证玩家/敌人明度与色彩层级。

### Task V4.2：升级战斗反馈

- 先做枪口闪光、弹道/子弹、命中火花、敌人死亡、经验和护盾拾取。
- 统一颜色职责、寿命、尺寸和层级，避免发光淹没角色。
- 需要新风格决定时先给三套预览。

### Task V4.3：压缩 HUD

- 移除战斗中常驻音频设置。
- 重排生命/护盾、经验/等级、波次/计时和状态提示。
- 保证 1280×720 和窄窗口不遮挡主要战斗区。

### Checkpoint E

- 一块完整战斗样板达到统一风格。
- 角色、弹幕、危险区、拾取物和 UI 信息层级清楚。
- 用户批准后才扩展到全地图和剩余批次。

## Phase 5：验收、性能与恢复生产

### Task V5.1：建立视觉回归

- 固定 1280×720 场景和多个战斗状态截图。
- 对 Alpha、pivot、方向、动画帧和 manifest 路径做自动校验。
- 保存 golden 图时必须有人审阅差异，不能只看像素阈值。

### Task V5.2：建立真实性能门

- 测平均、95/99 分位帧时间、draw call、节点数和纹理内存。
- 覆盖最高敌人数、连续射击、全屏 VFX、拾取物堆积和 HUD 更新。
- 发现实例化抖动后再决定是否引入对象池，不提前复杂化。

### Task V5.3：恢复资源审批

- 只有通过运行时证据门并经用户明确批准的资源可升为 `gameplay-approved`。
- 授权状态仍为 pending 的资源不得升为 `final`。
- 每个完成批次单独提交、验证、推送并发送完成邮件。

### Checkpoint F

- 视觉回归与性能门稳定。
- 资产登记、manifest、运行时路径和审批记录一致。
- 项目恢复批量美术生产。
